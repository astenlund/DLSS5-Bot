# DLSS5-Bot

DLSS5-Bot is the DLSS 5 mission for the [Pluri-Bot](https://github.com/astenlund/Pluri-Bot) engine: game-session work that adds and maintains NVIDIA DLSS 5 in PC games, shipped as one self-contained `.cmd` package. The project began as DLSS5-ADDER, published from a gist; this repository holds it from the legacy v67 release on. Deferred ideas are tracked as Exploring drafts in `.nightshift/FEATURES.md`; those entries are not approved work, so do not implement them unless the user explicitly asks. Work that spans the engine and this mission is tracked in Pluri-Bot's backlog.

## Layout

- `mission-dlss5/` holds the DLSS mission as loose files in the layout Explode writes: the `MISSION.md` template, `PROJECT.json` and the situational `INSTRUCTIONS.<name>.md` files. Mission text is not interpolated apart from the template's `{{placeholder}}` values, so it names state-block keys such as `dlssnr_patcher_store` instead of payload variables. Most behavior changes are mission changes; edit them here, never in a built package.
- `engine/engine.cmd` is the vendored engine file and `engine/pin.json` records its engine version, the Pluri-Bot tag and commit it comes from, and its SHA-256. `tools/Update-EnginePin.ps1 -Tag <tag>` pins a published Pluri-Bot release: it checks the release's engine file against the SHA-256 the release publishes and rewrites both files, so an engine update is one reviewable commit. There are no submodules, and the build works offline.
- `tools/Build-Package.ps1` assembles the package into `build/DLSS5-ADDER.cmd` from the pinned engine, refusing an engine file whose hash or version does not match its pin, or with `-PluriBotTree <path>` from a local Pluri-Bot working tree for building and testing an unreleased engine; `build/build-record.json` names the engine source, for a tree its commit and whether it was clean, and in `mission_clean` whether `mission-dlss5/` matched this repository's HEAD, since assembly embeds every file in that folder. From v1-1, publication accepts only a build from the pinned engine.
- `tests/` holds the release suite: `Test-DLSS5Adder.ps1` with the generated-prompt assertions, which loads the other `Test-DLSS5*.ps1` files, and `Hold-DLSS5Guard.ps1`, which holds a folder's guard from a separate process. The historical packages are in `tests/fixtures/`, with their SHA-256 in `tests/fixtures/SHA256SUMS`: the v22 and v49 packages the suite reads, and the legacy v67 package, the new line's first baseline. The cases that read the hello-world base run in Pluri-Bot against its own base.
- `tools/` also holds the suite runners (`Invoke-Suite.ps1`, `Invoke-SuiteOffscreen.ps1`, `Invoke-SuiteToFile.ps1`), `Compare-SuiteResults.ps1`, the parse and notes checks (`Parse-Candidate.ps1`, `Validate-Notes.ps1`), prompt rendering and parity (`Render-MissionPrompts.ps1`, `Compare-PromptParity.ps1`), the launch function comparison (`Compare-LaunchFunctions.ps1`), the line-ending normalizer (`Normalize-Endings.ps1`), the privacy sweep (`Invoke-PrivacySweep.ps1`) and the live host probes: `Probe-AccountCheck.ps1` runs the host's account check the way the engine does, without a window, while `Probe-ApprovalModes.ps1` opens host windows and `Probe-MissionMerge.ps1` runs a merge session in one, so the user runs those two. Probe records and other machine-generated outputs (suite outputs, results, remote snapshots) stay on the author's machine in the LocalAppData `release-records\` folder, never in this repository.
- `research/` holds research notes the project draws on. `records/` holds the import's record and, from the new line on, one record per release.

## Working rules

- Every source file is UTF-8 without a byte-order mark, ASCII unless a file says otherwise, with uniform CRLF line endings and one terminal newline; `.gitattributes` stores every file byte for byte.
- Run the suite only through `tools/Invoke-Suite.ps1`, which uses the off-screen runner, and under the PowerShell tool, not Git Bash, whose PATH breaks the git-unavailable case. The suite opens many console windows, so the runner puts it on a private desktop and, by the author's standing preference, switches the per-user default console host to the classic Windows Console Host for the run and restores the previous setting afterwards (from `test-runs\console-delegation-restore.json` in LocalAppData if a run was interrupted). Never run the suite in a way that shows windows on the user's screen, never start a second run while one is live (the runner refuses to), and after stopping or killing a run run `tools/Invoke-SuiteOffscreen.ps1 -RestoreOnly` at once. While building and fixing, run only the affected cases with `-Filter <regex>` or `-TestFile <names>`; a filter that selects nothing fails, and a `-TestFile` name the suite does not load is refused. A case whose assertions depend on what this machine's probes or live files return carries a `# live-input` comment. Judge a result from the output file, not the runner's console output alone.
- Before every push, run `tools/Invoke-PrivacySweep.ps1 -Range <outgoing range>` (for a first push, `-Range HEAD`); its literal terms live outside the repository, in the LocalAppData `release-records\sweep-terms.txt`, and a hit or a missing terms file stops the push.
- `astenlund/DLSS5-Bot` is never renamed, transferred or deleted: from v1-1 every copy reads its releases and refuses redirects, so a move would be a migration of its own.

## Publication

This is the legacy procedure that published DLSS5-ADDER to its gist, through legacy v67, kept here for reference: no package is published to the gist again, and the release procedure from v1-1, on GitHub Releases, replaces it when the repository-home design's Step 2 ships. Publishing is author-only and needs the author's GitHub access. Its folder names (`development\vNN-slug\`, `tests\`) are those of the LocalAppData layout the procedure ran in.

The gist write itself follows the DLSS5 bootstrap procedure of the `sync-gists` skill, which is authoritative for the gist identity, user confirmation before writing, the single update carrying both the bootstrap and README, and post-write verification. This section adds the release steps around that write.

1. Candidate: work in `development\vNN-slug\`, starting from a baseline copy of the canonical `DLSS5-ADDER.cmd`, and record the baseline's SHA-256. Bump both version markers, `rem DLSS5_BOOTSTRAP_VERSION=` and `$script:Dlss5PayloadBootstrapVersion`. Start from the previous release folder's scripts (`Build-Candidate.ps1`, `Verify-Candidate.ps1`, `Install-Canonical.ps1`, `Publication-Common.ps1`, `Prepare-Publication.ps1`, `Publish-Gist.ps1`, `Capture-PublicationSnapshot.ps1`, `Verify-Publication.ps1`, `Invoke-BaselineSuite.ps1`, `Test-BaselineSuite.ps1`, `Invoke-FilteredSuite.ps1`, `Invoke-PostReviewChecks.ps1`, `Compare-BaselineFailures.ps1`, `Invoke-SuiteOffscreen.ps1`, `Invoke-SuiteToFile.ps1`, `Validate-Notes.ps1`) and update their version, hash, and revision constants, including the version-named file names, consistently across the scripts. From v51, also start from the previous release folder's `mission-dlss5\`, `mission-hello-world\`, `Assemble-Package.ps1`, `Build-Base.ps1`, the interop suite (`Test-V49Interop.ps1` in v50, `Test-V50Interop.ps1` in v51, `Test-V51Interop.ps1` in v52, `Test-V52Interop.ps1` in v53, `Test-V53Interop.ps1` in v54, `Test-V54Interop.ps1` in v55, `Test-V55Interop.ps1` in v56, `Test-V56Interop.ps1` in v57, `Test-V57Interop.ps1` in v58, `Test-V58Interop.ps1` in v59, `Test-V59Interop.ps1` in v60, `Test-V60Interop.ps1` in v61, `Test-V61Interop.ps1` in v62, `Test-V62Interop.ps1` in v63, `Test-V63Interop.ps1` in v64, `Test-V64Interop.ps1` in v65, `Test-V65Interop.ps1` in v66, `Test-V66Interop.ps1` in v67, adapted to the previous release), `Get-PayloadDefinitions.ps1`, `Parse-Candidate.ps1`, and `Compare-PromptParity.ps1` with its `prompt-changes.json`, which `Verify-Candidate.ps1` runs; from v51 it renders the previous release's and the candidate's prompts through `Render-MissionPrompts.ps1`, so adapt them to the previous release's mission. From v51 the release folder also holds the live host probes (`Probe-AccountCheck.ps1`, and `Probe-ApprovalModes.ps1`, which the user runs since it opens host windows); their records must pass before review, and a release that changes no host launch behavior, as v52 to v67 do not, carries the previous release's records forward instead of rerunning them. From v60 the release folder also holds `Probe-MissionMerge.ps1`, the live merge probe the user runs with each host, since a merge is an agent session of its own; its records must pass before review, and a later release reruns it when it changes the merge prompt or the merge flow and otherwise carries its record forward. From v55, also start from `Compare-LaunchFunctions.ps1`, whose output (`launch-functions.txt`) shows the host launch functions textually unchanged (from v62, apart from the status lines it names, which no host argument, environment or start reads, each required once in its named place and removed from both sides) and so justifies carrying the records forward, and `Test-HelloBase.ps1`, which runs the hello-world base's own test headless (`suite-hello-base.txt`) and starts its package without a console window, so it runs directly rather than through the off-screen runner. Edit mission files there rather than in the package. `Build-Candidate.ps1` keeps an existing baseline with the expected hash, so it can be rerun after install; `Verify-Candidate.ps1` cannot, because it requires the canonical copy to still be the previous version.
2. Verify the candidate: UTF-8 without BOM, uniform CRLF, terminal newline, no unintended non-ASCII bytes, the payload parses, and its bootstrap identity reports the new version. Confirm the live canonical copy still matches the recorded baseline hash, and that edited test files stay CRLF and ASCII.
3. Test before review: run the suite only through the release folder's scripts, which use `Invoke-SuiteOffscreen.ps1`, and under the PowerShell tool, not Git Bash, whose PATH breaks the git-unavailable case. The suite opens many console windows, so the runner puts it on a private desktop and, by the user's standing preference, switches the per-user default console host to the classic Windows Console Host for the run and restores the previous setting afterwards (from `test-runs\console-delegation-restore.json` if a run was interrupted). Never run the suite in a way that shows windows on the user's screen. Never start a second suite run while one is live; the runner refuses to. After stopping or killing a run, run `Invoke-SuiteOffscreen.ps1 -RestoreOnly` at once to put the user's console host back. Run the baseline once, at the start of the release, with `Invoke-BaselineSuite.ps1`, which runs `tests\Test-DLSS5Adder.ps1` against the previous release's frozen copy and keeps each case's result in `baseline-results.json`. That copy is the previous release's candidate, so when a sibling release folder's `candidate-results.json` records a passing post-review run of those exact bytes, the script starts from it and the first baseline runs only what has changed since; with no such record it is a full run. Rerunning it runs only what an input changed: a test file changed only inside its cases reruns that file's cases, a rebuilt hello-world base or a changed hello-world mission reruns the cases that read them, and any other change to the test code, a historical package the tests read, a suite runner script, or a changed baseline reruns everything. A changed test file with no recorded results is carried when its guard stopped it before any case ran and otherwise reruns everything, as do a test file whose cases were all removed and a base that code outside a named case reads. A case whose assertions depend on what this machine's probes or live files return, rather than on a fixture, carries a `# live-input` comment in its body and reruns every time; a launch that only snapshots the hardware along the way does not count. From v58, a case that failed when last run also reruns every time, so a timeout is never carried; a guard failure, which stops its whole file, is carried. Machine tools and environment such as Git, `pwsh` and `PATH` are not tracked, so after changing them run the baseline with `-Full`. Every other result is carried forward, and the `NOTE` lines of the `suite-*.txt` output record what was. While building and fixing, run only the affected cases with `Invoke-FilteredSuite.ps1 -TestFile <names>` or `-Filter <regex>`. A filter that selects nothing fails, and a `-TestFile` name the suite does not load is refused. After updating the copied scripts' constants, run `Test-BaselineSuite.ps1`, the carry rules' own fixture tests, which need no console window. Each case's elapsed time is a `TIME` line in the output, and the slowest are listed as `SLOW` lines. Judge a result from the `suite-*.txt` files, not from the runner's console output alone.
4. Review: obtain a clean fresh-eyes review verdict over the candidate before the full checks, and record the cleared SHA-256 in `reviewed-candidate.sha256.txt`.
5. Full checks: run `Invoke-PostReviewChecks.ps1` once, on the bytes the reviewers cleared; it refuses any others. It runs the full candidate suite, the cross-version cases that run the previous release's updater against the candidate in the release folder's interop suite (`Test-V66Interop.ps1` in v67), the hello-world base test, the launch function comparison, the `Invoke-BaselineSuite.ps1` refresh, and the baseline comparison. The candidate passes every case; against the baseline, only the cases added or changed for this release fail, and the unchanged cases that read the release folder's rebuilt hello-world base, all listed in its `changed-cases.md`. A failure here reopens review: the fix changes the bytes, so it needs a clean review and this step again. When every check passes, it saves the candidate suite's per-case results as `candidate-results.json`, for the next release's baseline to start from; if they cannot be saved it says so, and that next baseline is a full run.
6. Install: replace the canonical AppData copy through the payload's own bootstrap lock, trust, and atomic-replacement functions, never by a direct file copy, and only while the canonical copy still has the baseline hash. Write trust before the replacement, then read back the installed hash and trust. From v50, trust is the whole-file entry for the candidate's published form plus the engine entry for its engine, and the AppData copy holds only the published form. When developing or installing the canonical copy, do not update the copies in game directories; each game copy picks up the published version through auto-update on its next launch.
7. Publish: publish the installed canonical copy, after confirming its SHA-256 equals the reviewed candidate's. The GitHub gist API returns at most 1 MB of content per file and auto-update refuses a truncated file, so the published file must stay under 1 MB. Before writing, confirm the gist is still at the revision recorded by the previous release (its `published-revision.txt`) and still holds the previous version's SHA-256. Update the README's version and SHA-256 from the exact published bytes, requiring exactly one occurrence of each replaced README anchor.
8. Verify: from one immutable resulting revision, download both files and require the exact intended bytes; the README must state the new version and hash and no longer contain the old hash.
9. Record: keep the scripts, diffs, suite outputs, `baseline-results.json`, `candidate-results.json`, remote snapshots, and `published-revision.txt` in the release folder.
10. Backlog: in the same pass as the publication, without being asked, record each tracked item the release shipped by the full procedure of the `.nightshift` index that owns it (`FEATURES.md` for a feature or slice, `BUGS.md` for a bug, `QUICK_WINS.md` for a quick win), with the published revision standing in for a commit. A shipped slice leaves its feature active, and the feature record says the slice shipped, with the revision and SHA-256; the feature itself ships only with its last slice. A release that ships no tracked item needs no backlog edit. Then rerun `/nightshift:ready` to check that the backlog parses.
