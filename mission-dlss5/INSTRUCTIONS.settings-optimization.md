## Settings research and A/B optimization

This file extends operating rules 2 (settings research) and 6 (verification) of the DLSS 5 ADDER operating prompt, and every rule of that prompt still applies.

Version 23 removes the request to rank image quality, temporal stability, performance, latency, and VRAM as abstract priorities.

After required primary-display runtime and visual validation passes, the controller asks exactly `Would you like to optimize image quality and performance now?` After trimming ASCII whitespace and applying ordinal case-insensitive comparison, exactly `yes` or `y` accepts and exactly `no` or `n` declines. An empty response also declines. Any other response receives one concise clarification that repeats the question and adds `Answer yes or no.`, under the same grammar; a second unmatched response, EOF, noninteractive execution, or prompt failure declines. Decline records that optimization was offered and declined in the existing notes field, or, where no game notes file exists in a session that must not create one, follows the absent-notes rule of operating rule 7 (persistent game notes), starts no settings research, and continues ordinary final verification and reporting without treating optimization as pending or failed.

When optional optimization is accepted, the controller first asks: `Do you have a hard minimum frame rate? If yes, what is it in FPS?` A numeric floor is an ASCII base-10 integer from 1 through 1000 followed optionally by surrounding whitespace; units are FPS. After trimming ASCII spaces and tabs and applying ordinal case-insensitive comparison, exactly `no`, `n`, `none`, `not sure`, `unsure`, `skip`, or an empty response means no numeric hard floor and does not block optimization; EOF, noninteractive execution, an unavailable prompt API, or prompt failure likewise means no numeric hard floor. Any other response receives one concise clarification that repeats the question and adds `Answer with a number from 1 to 1000, or no.`; a second response that is neither a valid floor nor a no-floor token becomes no numeric hard floor rather than blocking or inventing a value. A valid explicit floor is a hard constraint.

After that question, optimization is an iterative pretty-versus-smooth judgment:

1. Preserve the accepted runtime-valid configuration as baseline.
2. Rank remaining settings by expected performance gain relative to likely visible quality loss, starting with the largest promising gains.
3. Keep user-declared exclusions, such as an unwanted visual feature, out of later candidates.
4. Test one independent setting at a time in the same representative scene, route, resolution, workload, and warm-up conditions.
5. Ask for observed performance and the user's practical visual judgment.
6. Retain or revert the candidate according to that evidence. If a floor-meeting baseline falls below the floor, the candidate is always reverted. While no tested baseline meets the floor, a measured improvement may be retained provisionally so cumulative independent changes can approach it, but that state cannot be called final or good enough.
7. Continue with the best remaining candidate until the user says the result is good enough when no numeric floor exists, the hard FPS floor is met with acceptable quality, or no worthwhile candidate remains. If no tested configuration meets a valid floor, report the constraint as unmet. Before restoration, accept only a user-volunteered `remove` token after trimming and case normalization, or a replacement numeric floor that reuses the original 1 through 1000 grammar and is strictly lower than the current floor. `remove` clears the floor and makes the current best provisional baseline ordinary; a valid lower floor replaces the old one and immediately reclassifies every measured baseline against it. Continue the loop if the current best still misses the replacement floor; otherwise the user may judge it under the ordinary stopping rule. Any other response leaves the floor unchanged without a second clarification. With no valid change, restore the last floor-meeting baseline, or the original accepted baseline when none met the floor, and end without claiming optimization success.
8. Re-run affected runtime and visual validation for the selected final configuration.

For a numeric hard floor, each baseline and candidate pass uses the same warm-up and 15-second observation. Warm-up starts only after loading finishes, player control returns, and no loading indicator is visible, then holds the representative scene, camera, and workload unchanged for 30 seconds. A scene transition, loading indicator, settings or resolution change, or user-identified compilation or loading hitch restarts the 30-second warm-up. If the user cannot establish those conditions, the measurement is invalid. After warm-up, ask `What was the lowest stable FPS you observed during that pass?` Define `<fps-number>` by the exact ASCII regex `(?:[1-9][0-9]{0,2}(?:\.[0-9])?|1000(?:\.0)?)`. A response is either one `<fps-number>` or two `<fps-number>` tokens separated by one ASCII hyphen, with zero or more ASCII spaces or tabs around the complete response and around the hyphen. One optional `fps` suffix may follow the final number after one or more ASCII spaces or tabs; only that suffix is compared ordinal case-insensitively. No other whitespace, leading zero, leading or trailing decimal point, or second fractional digit is valid. A range uses its lower endpoint and requires the second endpoint to be greater than or equal to the first. Compare the selected decimal directly with the integer floor without rounding. The user decides whether a moment was a stable reading rather than a loading hitch; no telemetry or percentile metric is required. Missing, reversed-range, nonnumeric, out-of-range, or qualified-only input receives one remeasurement request. A second invalid or ambiguous result leaves the candidate unverified and restores the accepted baseline before further testing.

Candidate application failure rejects that candidate and restores the last accepted baseline before another test. Restoration must be measured or directly re-read and match the retained baseline. Partial, failed, or unverified restoration stops optimization immediately, records the observed settings and attempted prior values as interruption evidence, and permits no further candidate test. Recovery requires the user either to establish and verify a chosen baseline explicitly or to adopt the observed settings as a new unverified baseline before a new optimization generation starts. A game crash, measurement abort, or EOF during iterative judgment rejects the active candidate; after restart, the controller asks the user to re-enter or restore the prior values they know and does not resume until the same scene and baseline are re-established. If those values are unavailable, the user may instead explicitly adopt the observed settings as a new unverified baseline. If the agent or controller terminates abruptly, no automatic write is attempted: the next session follows that same explicit restore-or-adopt recovery. Until affected runtime and visual validation passes, the notes record optimization as interrupted rather than successful. Where no game notes file exists in a session that must not create one, the interruption evidence and this status follow the absent-notes rule of operating rule 7.

The controller does not require the user to quantify a quality floor, resource ceiling, or bang-for-buck rule unless the user volunteers one. It infers the next experiment from measured and visual evidence and lets the user stop.

Settings research is agent work, not bootstrap-persisted state, and begins in a read-only background task once these minimum inputs are known: game title and build, installed graphics or gameplay mods, active renderer and injection route, GPU model and VRAM, display resolution and refresh rate, and one representative scene's warmed FPS measurement with the active resolution, upscaler or antialiasing mode, frame generation, ray reconstruction, and major preset or overrides. Missing optional CPU, system-memory, or detailed frame-time data does not delay research; a missing minimum input does.

The research result is a concise ordered candidate list rather than a rigid user questionnaire. Each candidate names the setting and proposed change, expected performance direction and rough magnitude when evidence supports one, likely visible cost, known compatibility caution, confidence, and source basis. A candidate missing its setting or proposed change is discarded; missing optional estimates lower confidence. Results remain provisional until relevant compatibility and runtime facts are validated. If the task cannot produce a usable candidate list, it returns one short unavailable reason and the controller keeps its bounded best-evidence sequence.

When research starts, the controller retains one in-memory optimization generation containing the exact minimum inputs above, current hard-floor state, accepted baseline settings, scene identity, and the current normalized set of user-declared exclusions. When runtime validation permits A/B testing before research returns, the controller starts immediately using its best current evidence. It does not wait. A research result may update the remaining candidate order and compatibility cautions only while that generation is still active and every retained input and exclusion still matches; otherwise the result is discarded as stale. Every merge also filters candidates against the current exclusion set. Changing exclusions, ending optimization, or starting a replacement research task invalidates the generation. Completed measurements remain valid evidence for unchanged inputs and still-permitted settings even when the shortlist changes. A research failure leaves the controller's bounded best-evidence sequence in place and is recorded as unavailable rather than blocking otherwise safe tests.
