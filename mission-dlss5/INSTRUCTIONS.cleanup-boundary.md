## Automatic cleanup boundary

This file extends operating rules 5 (transactional changes) and 6 (verification) of the DLSS 5 ADDER operating prompt, and every rule of that prompt still applies.

Before the final completion report, inventory artifacts created during the session, including every game-directory path the session created or changed regardless of who created it (the controller, research or review subagents, or a tool side effect), and include proposed cleanup targets in the required review. After the required review and verification are clean, automatically remove only artifacts eligible under the closed ownership rules below, and only when their owning lifecycle permits removal. For remaining disposable or unexplained session-created files, proactively present the exact targets and recovery implications and ask whether to delete them, as one yes-or-no question asked with the host's structured question tool when one exists (AskUserQuestion in Claude Code) and in plain text otherwise. List every exact path in the question itself and ask whether to delete all of them; yes deletes every listed path, and no keeps them all. If the user instead names specific paths to delete, delete only those exact listed paths; an existing explicit approval covering those exact targets and recovery implications is sufficient. Preserve required runtime files, user backups, and diagnostic evidence still needed for recovery. If there are no eligible targets, continue without a cleanup question. If confirmation is declined, unanswered, or unavailable, retain the files and record their exact paths in the applicable session notes. Cleanup failure retains and reports the affected paths without changing a successful installation result.

Obtain the game-directory part of the inventory by running the game-local DLSS5-ADDER.cmd from the game directory with --internal-session-changes and that file's absolute path as its first argument. Also pass the session_snapshot_id from the state block as the second argument when it is non-empty, and no second argument otherwise. It prints one compact JSON line: state ok with entries, each a porcelain-style status and path that differs from the startup state, excluding the updater exceptions and the game notes; or state unavailable with a reason. Without a snapshot ID, in a Git game directory, Git runs inside the bootstrap and each entry is a Git porcelain status and repository-relative path that differs from the clean startup preflight. With a snapshot ID, which a non-Git game directory and a diagnosis-only session receive, the bootstrap compares the current directory with the snapshot it captured before launch, even if Git has become available since, and each path is relative to the game directory: `?? ` marks an added file, link, or directory (with a trailing slash), ` D ` a removed one, and ` M ` a file or link whose kind, size, or last-write time changed or a directory whose kind changed, and an added or removed directory, including one that a file replaced or that replaced a file, stands for its whole subtree. The snapshot compares only size and last-write time, so an edit that preserves both is not reported. The unavailable reasons are not-a-git-repository (a non-Git game directory without a snapshot ID), git-unavailable (Git metadata exists but Git is unavailable, and no snapshot ID was passed), git-inspection-failed (Git metadata exists but Git cannot inspect the repository, and no snapshot ID was passed), snapshot-missing, and snapshot-invalid; on any unavailable report, inventory the game directory by other read-only means. Exit 0 means a valid report, 1 a wrapper precheck failure, 2 invalid arguments, and 4 an inspection failure; any nonzero exit leaves the inventory incomplete, is reported, and is not retried in a loop. Classify each entry as an intended installation change kept for the user to commit, a required runtime file, or a disposable or unexplained artifact.

Successful cleanup is quiet and automatic for exact artifacts whose ownership is established by one of the closed rules below:

- The extracted temporary PowerShell payload.
- The generated agent prompt, the situational instruction files written for the same launch into its `prompts\dlss5-agent-sections-<id>\` folder, and that folder, after the exact agent process exits, or after process creation confirms that no process or handle was created, when current-run path, length, hash, type, and non-reparse identity still match; the folder is removed only once every file in it was removed. The bootstrap removes them itself, and the agent never deletes or edits them. Ambiguous launch outcome preserves them.
- Completed per-launch notification files and directories whose launch ID, in-memory completion token, and required token-bound worker plus Claude watcher markers match the current run.
- An obsolete fixed-path `updates\last-failure.json` immediately after the current worker has durably written valid `no-update` or `staged` terminal status and before it attempts any notification or marker creation, but only when the prior diagnostic is a regular non-reparse file with the complete exact schema and the shared AppData guard passes immediately before deletion.
- A prior-launch session directory older than 24 hours only through the bootstrap's complete stale-session ownership and age checks.
- The current run's own reserved `sessions\.creating-<launch-id>` state on channel-setup abort, an abandoned reserved `sessions\.creating-<launch-id>` directory from any prior launch, both only under the bootstrap lock, and a resumable reserved `sessions\.cleanup-<launch-id>` directory, regardless of age, without the bootstrap lock because the locked live-to-cleanup rename already proved no participant remains, with the shared guard repeated before every deletion; each only through the bootstrap's closed child grammar and fixed deletion order. The reserved namespaces are updater state, never user storage.
- The current launch's own `snapshots\<snapshot-id>.json` session snapshot, which the bootstrap removes after its end-of-session listing; an abandoned `snapshots\.creating-<snapshot-id>.json` from an interrupted launch, under the bootstrap lock; and a prior launch's snapshot whose validated created_at is older than 24 hours, under the bootstrap lock. The agent never deletes or edits session snapshots.
- A consumed or redundant trusted stage pair at the two fixed AppData paths when strict `stage.json` fields, gist identity, version, SHA-256, and immutable checksum match the `.cmd`. This updater-owned pair may have been created by an earlier run. The only checksum-mismatched removal is the worker's same-lock replacement case where matching fetched bytes already have immutable trust and directly disprove the existing pair.
- A metadata-only stage cleanup remainder at the fixed `stage.json` path when its complete schema and pinned identity validate and the staged `.cmd` is absent. It is non-executable and removed only under the bootstrap lock after the bootstrap's complete root-to-leaf containment and non-reparse recheck plus a second metadata read.
- Successful same-directory candidates and internal `.rollback-<guid>` transaction files after destination readback proves recovery is no longer needed.

Automatic cleanup occurs only after the owning operation succeeds and required review and verification are clean. Cleanup failure produces a concise warning and exact retained path but does not convert a successful game update into a false failure.

Pre-existing files outside those fixed ownership rules, unowned downloads, user-created backups, ambiguous paths, tracked content not created by the current run, and recovery artifacts still required after failure are not automatically deleted. Agent-created installation scratch outside the bootstrap's fixed paths still requires exact-target and recoverability confirmation; v23 defines no transaction manifest. `DLSS5-ADDER.cmd.bkp` is a retained user rollback and is never part of automatic cleanup. The implementation never broadens a cleanup target through an unresolved variable, wildcard, workspace root, or recursive parent deletion.

`Invoke-Dlss5AtomicReplacement` creates `.rollback-<guid>` only in the destination directory when a destination exists. After verified replacement and byte readback, that exact internal rollback is no longer recovery authority and is deleted automatically. If replacement, verification, restoration, or rollback cleanup fails, the helper preserves every remaining candidate and rollback path, reports them exactly, and does not clean them on a later launch without confirmation. These internal rollback files never use `.bkp` naming and never authorize cleanup of a sibling path.

The batch wrapper no longer asks whether to delete its generated payload. `Invoke-Dlss5InteractiveAgent` no longer asks whether to delete its generated prompt. The operating prompt no longer describes a clean review as permitting a routine cleanup-confirmation request; it authorizes automatic owned-artifact cleanup within this boundary.
